## Change brief

The DM (`orchestrator.ts`) or the host (`session.gateway.ts`, `REQUEST_ROLL`)
asks for a check by broadcasting `ROLL_REQUESTED { pending_action_id, prompt,
expression, authorized_character_ids }` and parking the session on
`WAITING_FOR_ROLL`. `useSession.applyEvent` drops the event, so spec-doc.md
§5.4 is unplayable from the browser: the player never sees what was asked
(FR-305). An authorized character's `ROLL_DICE` closes the action and the
gateway broadcasts `PENDING_ACTION_COMPLETED { pending_action_id, … }`.

Client-only: fold open requests out of the event log, render a card above the
composer. No new command, event, snapshot field or migration.

## Specification

AC-1  `applyPending(current, event)` (`apps/web/src/session/pending.ts`, pure)
      appends a `PendingRoll` on `ROLL_REQUESTED`, removes the matching one on
      `PENDING_ACTION_COMPLETED`, ignores a completion for an id it does not
      hold and every other event type, and never holds two cards with the same
      id (FR-305).
AC-2  Behind `applyEvent`'s high-water guard, a request, its completion, and a
      replay that re-delivers both leave no card: two rolls in quick
      succession neither duplicate nor resurrect a card.
AC-3  `useSession` returns `pending`, folded in `applyEvent` after the guard;
      a fresh or reloaded tab rebuilds it from `resume`'s replay alone.
AC-4  `PendingRollCard` sits above the composer and shows a card for each
      entry in `pending`, inside a `role="status"` region that stays mounted
      so the request is announced (NFR-402), marked with a glyph plus a text
      label (NFR-403); it shows the prompt and the requested expression.
AC-5  The Roll button appears only when the seated `characterId` is in
      `authorized_character_ids`, and calls the existing `roll(expression)`;
      the card clears only from `PENDING_ACTION_COMPLETED`, never
      optimistically. Everyone else sees "Waiting on …" with names resolved
      from the `['characters', campaignId]` query.
AC-6  typecheck / lint / format / test green.

## Decisions

- **D-1 — The high-water guard stays in `applyEvent`.** The reducer is
  idempotent on its own (duplicate request, unknown completion), but only the
  sequence guard stops a replayed request resurrecting a closed card. The
  guard is a pure `isFresh(event, highWater)` in `pending.ts` that both
  `applyEvent` and the test use, so AC-2 exercises the real guard.
- **D-2 — Roll is disabled while mutations are refused.** Same gate as the
  sheet's roll buttons (`acceptsMutations`, U1.0): a pause keeps the card up
  with the button disabled. After `SESSION_ENDED` the card is hidden — ending
  does not close the `pending_actions` row, and "Waiting on …" forever on an
  ended session would be false.
- **D-3 — Expression is shown, not enforced.** The server closes by
  character, not expression (M5 decision, summary.md §6).
- **D-4 — Replay is not gap-free.** A live event that beats the `resume` ack
  moves the high-water mark past the replayed tail (pre-existing, not fixed
  here); a request in that tail is then lost until the next reload. The card
  inherits this; the PR says so.
- **D-5 — Tests.** Pure reducer unit-tested; the card driven by hand (epic
  #72: no DOM testing library).
- **D-6 — `docs/ui-coverage.md` does not exist** on any branch; the issue
  text (its §4.2 source) is the spec used.
