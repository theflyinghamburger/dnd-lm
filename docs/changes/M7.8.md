## Change brief

Two half-tasks with one thread (#26): *who changed which provider setting*, and
*which connection served this turn*.

Today a platform admin can create a connection, replace its key, disable it, and
delete it, and the only trace is the row's `updated_at` — which the next write
overwrites. And a resolution's events record what the DM said and what it cost
in tokens, but not which connection produced it, so a per-connection failure
rate or spend cannot be computed from the event log at all. Both are the same
question asked at two layers: attribution.

The constraint that shapes the whole change is that neither half may become a
new way to leak a key. The audit records *field names*, never values, and the
resolution events carry an id and a model name, both of which the admin surface
already exposes.

## Specification

AC-1  Each of create, update, replace-key, delete, enable and disable appends
      exactly one `provider_connection_audit` row carrying the acting user, the
      action, the changed field names, and the time (FR-805, NFR-502).
AC-2  No column of an audit row ever holds a value — no key, no ciphertext, no
      URL, no label — only field *names*. Asserted by scanning the whole row.
AC-3  A `replaced_key` row's `changed_fields` is exactly `['api_key']`.
AC-4  A mutation that fails (an M7.3 URL rejection, a missing row, an in-use
      delete) writes no audit row: the audit is in the same transaction as the
      change it records.
AC-5  Deleting a connection leaves its audit history in place, including the
      `deleted` row itself.
AC-6  A committed resolution's `DM_NARRATION` payload carries
      `provider_connection_id` and `model_id`.
AC-7  A failed resolution's `DM_RESOLUTION_FAILED` payload carries both, with a
      null connection where no connection was resolved (`NO_PROVIDER`).
AC-8  Two campaigns running on two connections each tag their own turns; neither
      turn carries the other's connection id.
AC-9  The resolution span carries `provider_connection_id` alongside the
      existing `dm.cost_usd`, so spend is attributable per connection without
      reading the event log (NFR-502).
AC-10 A per-connection failure-rate and cost query over `session_events` is
      stated in the pull request and runs against the schema this change
      leaves behind.
AC-11 `pnpm test` green against live Postgres, `pnpm db:check` clean,
      typecheck / lint / format green.

## Decisions

- **The audit table has no foreign key to `provider_connections`.** An audit row
  must outlive the row it audits — `deleted` is one of the six actions, and a
  cascade would erase exactly the record that matters most. `connection_id` is a
  plain `uuid`, and `actor_user_id` keeps its foreign key with `ON DELETE SET
  NULL` so removing a user redacts the actor rather than destroying the history.
  This is the standard audit-log trade of referential integrity for durability,
  and it is deliberate rather than an oversight.

- **`changed_fields` is a diff of the admin DTO against the stored row**, not a
  list of the keys the request happened to carry. A PATCH that re-sends the
  current label records nothing changed; one that moves the base URL records
  `base_url`. The names are the *column* names, so a reader of the audit table
  does not have to know the API's camelCase.

- **An `enabled` flip is its own action.** `enabled: false` in an update makes
  the row `disabled`, not `updated`, because "who turned this off" is the
  question the table exists to answer. When an update changes `enabled` *and*
  other fields, the action follows `enabled` and `changed_fields` still lists
  everything that moved.

- **A no-op update still writes a row with empty `changed_fields`.** Someone
  pressed save; that is a fact about the system, and "exactly one row per
  successful mutation" is a rule worth keeping simple enough to assert.

- **A *Test connection* press (M7.5) is not audited.** It changes no
  configuration; it writes a result cache. Auditing it would make the table's
  meaning "things admins did" rather than "changes to provider configuration",
  and the first is not a question anyone asked.

- **Attribution rides on the graph state, next to `model`.** The graph already
  carries the model that ran the turn so the commit can price it; the connection
  id travels the same way, which means the resume-after-roll path gets it for
  free rather than through a second lookup that could disagree.

- **No new schema in `packages/contracts` for the event payloads.**
  `EventEnvelope.payload` is deliberately an open record ("event types are
  domain vocabulary, added per milestone"), and there is no per-type payload
  schema to extend. The two fields are additive, so a client that does not know
  them is unaffected.

## Plan

1. `provider_connection_audit` table + action enum in `schema.ts`;
   `pnpm db:generate`; add the table to the harness `TRUNCATE`. — AC-1, AC-11
2. `ProviderSecrets.replaceKey` takes an optional executor so the re-encrypt can
   join the caller's transaction. — AC-1, AC-4
3. `ProviderConnectionsService`: each mutation becomes one transaction that
   writes its change and its audit row; the controller passes the acting user
   to update, delete and replace-key. — AC-1..AC-5
4. `SourcedProvider.connectionId`; the graph state carries it beside `model`. — AC-6..AC-8
5. Commit and failure payloads carry `provider_connection_id` / `model_id`;
   `reportFailure` takes the attribution it should record. — AC-6, AC-7
6. `provider_connection_id` on the resolution span. — AC-9
7. Tests: an audit e2e per mutation type plus the rollback and delete cases;
   attribution assertions on the existing two-connection e2e. — AC-1..AC-8
8. Full suite, `db:check`, typecheck / lint / format; run the query in AC-10. — AC-10, AC-11

Two things learned while implementing, both recorded above as decisions rather
than discovered later: `ProviderSecrets.replaceKey` had to take an executor for
the key change and its audit row to share a transaction, and the graph state was
the right carrier for the connection id because the resume-after-roll path then
reports the connection the turn actually used.
