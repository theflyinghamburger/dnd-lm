## Change brief

M7.1–M7.5 built the provider surface: rows, keys, an SSRF wall, an
authorization boundary, adapters and a test action. All of it is reachable only
by `curl`. #24 is the two screens that make it usable, for two audiences that
must see different things.

**Admin → Providers** is where connections are created, tested, edited,
enabled, and deleted. The rule that shapes every form on it: the key is
write-only end to end. It is typed once on creation, replaced by typing a new
value, and never read back — not because a filter hides it, but because no
response this page receives carries it (M7.2/M7.4). `••••{last4}` is the whole
display.

**Campaign → Settings** is where a host picks a provider from the *redacted*
enabled list — identity and model, structurally unable to carry a URL or a key
— and sets the FR-506 knobs.

The knobs needed a shape and nothing defined one (CL-001), and the question of
whether they should reach the DM's prompt in this change needed an answer
(CL-002). Both are recorded above rather than guessed in code, as spec-doc.md
§16 asks.

## Specification

AC-1   `GET /api/campaigns/:id/dm-settings` returns the selected provider and
       the three knobs; any member may read it (FR-506).
AC-2   `PATCH /api/campaigns/:id/dm-settings` writes any subset of the knobs;
       host-or-admin on that campaign only, a player gets 403.
AC-3   A value outside a knob's vocabulary is refused with 400, as is an empty
       write.
AC-4   A knob write merges into `campaigns.settings`: the provider selection
       and the trigger settings that share the column are untouched, and a knob
       can be cleared with `null`.
AC-5   A second host of the same campaign sees a knob another host set.
AC-6   The admin page lists every connection with kind, model, enabled state,
       and its last test result (M7.5's stored fields), and offers Test, Edit
       and Delete per row.
AC-7   The create form takes the key once; the edit form has no key field at
       all, so saving a label cannot blank a credential. Replacing a key is its
       own action.
AC-8   No file in `apps/web/src` reads a key off a connection object, no key
       input is anything but a password field, there is no reveal affordance,
       and `apiKey` is named only on the two write calls that take one
       (NFR-305).
AC-9   Validation messages are the server's: a refused URL shows M7.3's reason,
       an in-use delete names the campaigns from M7.4's 409, and a failed save
       leaves the form's contents alone.
AC-10  The provider dropdown is built from `GET /api/providers`, whose
       `HostConnection` shape has no URL and no key field.
AC-11  `pnpm test` green against live Postgres, typecheck / lint / format
       green, `pnpm build` builds the web app.

## Decisions

- **The knobs get their own endpoint; selecting a provider keeps M7.4's.**
  `PATCH :id/provider` validates the reference against the enabled connections;
  the knobs have nothing equivalent to validate against. One endpoint per
  concern beats one endpoint with two validation stories, and it leaves the
  M7.4 write — already tested and already used by the DM path — untouched.

- **Stored knob values are parsed on read, not cast.** A value written by an
  older build, or by hand, that is no longer in the vocabulary reads as "not
  set" rather than reaching a client that believes the type.

- **The pages live inside the Lobby, not behind a router.** The app has two
  views switched by state and no router; adding one for two screens would be
  the largest thing in the change. The Providers button appears when the user
  is a platform admin by the same definition the API uses (an `admin`
  membership in any campaign) — courtesy, not the control, which is
  `AdminGuard`.

- **The write-only key rule is enforced by a source scan, not a DOM test.**
  `apps/web/src/key-handling.test.ts` asserts the property over the whole web
  tree: no `.apiKey` read anywhere, `apiKeyLast4` and `••••` present, every key
  input a password field, `apiKey:` named only where a key is legitimately
  sent. The claim is about what the code can do, not one rendered state, and it
  needs no DOM library — which keeps the web app's dependency list where it is.

- **The delete confirmation names the campaigns from the server's refusal.**
  Nothing lists which campaigns use a connection before you try, and inventing
  an endpoint for it would duplicate the rule the 409 already enforces. Confirm
  → attempt → the refusal names them.

- **`verification` is `assumable`, not `clear`.** #24's exit criteria are
  manual click-throughs. What is automated here is the API behaviour and the
  key-handling property; the click-through itself was not performed, and the
  pull request says so rather than implying a green suite covered it.

Review follow-up: `describe` was module-private to the admin page, so the two
surfaces this change builds rendered rejections by two different policies — the
campaign settings screen showed a bare code and threw away the explanation the
same change added `ApiError.body` to carry. It is `describeApiError` in
`api.ts` now, used by both.

A second review pass added the admin list's error state — a failed read left the
page blank, with no loading line, no empty state and no alert. Two findings from
that pass are deliberately not acted on: `maxTokens` cannot be null or absent on
a stored row (`notNull().default(1024)` in the schema), so the form cannot
invent one; and component tests for the interactive halves are the gap this
work item already discloses below rather than a new one.

**Not covered by tests, stated plainly:** the click-through itself. #24's exit
criteria are manual flows in a browser; this change has no browser automation
and adding one is a larger decision than the feature. What is asserted is every
API behaviour behind those flows and the key-handling property of the source.
