# Rollback plan — M8.1

**Code.** Nothing reads or writes `campaign_notes` in this change, so reverting
the PR changes no runtime behaviour. Reverting the schema without dropping the
table would make the next `pnpm db:generate` emit a `DROP TABLE`; do both
together as below.

**Schema:**

```sql
DROP TABLE "campaign_notes";
DROP TYPE "public"."note_type";
DROP TYPE "public"."note_spoiler_level";
DROP TYPE "public"."note_status";
```

Then delete `apps/api/drizzle/0010_dry_marrow.sql`, `meta/0010_snapshot.json`, its
`_journal.json` entry, and the matching `drizzle.__drizzle_migrations` row, so
`pnpm db:check` agrees with the committed migrations again.

**Order once M8.2–M8.5 or P4.1 have landed on top.** Those changes read and
write the table; revert them first, or every notes request and DM turn that
retrieves notes fails once the table is gone. After P4.1.1, the
`campaign_sources` FK on `source_id` goes with the table.

**Data lost.** Every note. Hand-authored notes are not reconstructible from
anything else; extracted ones can be regenerated from `campaign_sources` once
P4.1 exists. If the table holds real data, dump it first:

```sql
\copy campaign_notes (id, campaign_id, slug, type, title, body_md, frontmatter, spoiler_level, chapter, status, source_id, created_at, updated_at) TO 'campaign_notes.csv' CSV HEADER
```

(`tsv` is omitted — it is regenerated on restore.)

**Right after merge, before anything writes to it**, the table is empty and
rollback loses nothing.
