## Change brief

A player joining a campaign has two ways to get a character: pick one of the six
pregens, or have someone post a hand-written JSON sheet with curl. Anyone who
already plays this character elsewhere has to retype it.

Character sheets exported from D&D Beyond are **form-fillable PDFs**: the values
are form fields with stable, well-known names (`CharacterName`, `STR`,
`PerceptionProf`, `MaxHP`). Reading one is deterministic field mapping — no model
call, no OCR, no heuristics. This adds that as a second input to the import path
that already exists.

Two things the example sheet exposed, both answered in `clarifications` above:
it is multiclass (`Artificer 5 / Wizard 2`), which `className` + `level` cannot
represent; and it carries 95 spells and 4 attacks, which `CharacterSheet` had no
field for. Both are now modelled rather than dropped.

## Specification

- **AC-1** — A member of a campaign can upload a form-fillable character sheet
  PDF and get a real character in that campaign (FR-402).
- **AC-2** — The PDF crosses the *same* `ImportCharacterRequest` schema the JSON
  route uses, so a PDF cannot smuggle a derived value past `.strict()` any more
  than a hand-written body can (FR-401, D-3).
- **AC-3** — No derived value is read from the file. Modifiers, saves, skill
  totals, passive scores and initiative are recomputed by `deriveSheet` (FR-401).
- **AC-4** — A multiclass sheet imports with every class and its level, and the
  character's level is their sum (FR-402).
- **AC-5** — Spells carry the level of the banner they sit under, and prepared is
  distinguished from merely known.
- **AC-6** — Anything the schema cannot hold is reported back to the uploader by
  name, never dropped silently (FR-402).
- **AC-7** — The upload is bounded and type-checked at the trust boundary: 8 MB
  ceiling enforced before the body is read, and `%PDF-` magic bytes rather than
  the client-declared MIME type (NFR-301).
- **AC-8** — A non-member is refused (NFR-302), by the guard that already covers
  every other route on this controller.
- **AC-9** — A sheet whose stated proficiency bonus contradicts the parsed class
  line is refused rather than imported at the wrong level, and the refusal carries
  the numbers a client needs to offer a way past it.
- **AC-10** — A sheet stored before `classes[]` existed still reads, derives and
  renders; a structurally corrupt one fails at the read boundary rather than deep
  inside `deriveSheet`, and its shape is not disclosed to the caller.
- **AC-11** — The owner of a character, or a host of the campaign, can delete it.
  Deletion is refused while the character is named in an open pending action, and
  past rolls survive it with their modifier provenance intact (FR-302).
- **AC-12** — Race, background, hit dice and senses are imported rather than
  reported as lost.
- **AC-13** — The DM sees a character's attacks and the spells that are actually
  available — cantrips and prepared — with the remainder counted, not listed.
- **AC-14** — The state layer never exceeds its declared budget, measured on the
  text that is sent rather than the token count that is recorded (FR-701, NFR-502).

## Decisions

**The reader walks page annotations, not an AcroForm.** The exported sheets carry
1981 widget annotations and **no `/AcroForm` entry in the document catalogue**.
Every form-field helper that starts from `catalog.AcroForm.Fields` — pdf-lib's
`getForm()`, pdf.js's `getFieldObjects()` — therefore returns nothing on exactly
the files this feature exists to read. Walking each page's annotations is both the
path that works and the one that yields the page and rectangle the spell grouping
needs. The e2e fixture deliberately omits `/AcroForm` so a regression here fails.

**Spell level comes from page geometry.** The `=== 1st LEVEL ===` banners are
their own form fields, not part of the spell list, so nothing but position ties a
spell to its level. The reader sorts by page then descending `y` and carries the
last banner down — the way a person reads the page. Marked `ponytail:` at the call
site with its ceiling: one column per page.

**The file's proficiency bonus is a check, not an input.** It is the one derived
number that depends on level alone, so a disagreement means the class line was
misparsed. Importing a level-7 character as level 5 would skew every roll they
make, so this refuses rather than guessing — the only place the file's own
arithmetic is read at all.

**`level` moved from stored to derived.** With `classes[]`, the character's level
is a sum, and the rule that derived values are never stored (D-3) applies to it
like everything else. `DerivedSheet` gained `level` and `className`.

**`characters.level` had to be dropped.** It was a generated column over
`sheet->>'level'` — a key `classes[]` removed, so it evaluated to `NULL` on every
new row (verified against Postgres). It cannot be repaired: summing a JSONB array
needs `jsonb_array_elements`, a set-returning function, which a generated column
may not contain. Nothing read it, and a stored derived value is what D-3 forbids
anyway. Dropping it is the only schema change here; the sheet's own shape lives in
`jsonb` and needs no DDL.

**Stored sheets are reshaped on read, not migrated.** `parseStoredSheet` replaces
the six unchecked `row.sheet as CharacterSheet` casts — the actual defect, since a
cast asserts a shape nobody verified. It parses, so a corrupt row fails at the
boundary naming the field. A migration that must be run is one that can be
skipped, and skipping it would break every character read; this cannot be skipped.
See `M4.7.migration-plan.md`.

**The `ProfBonus` refusal is escapable, but only deliberately.** `?confirmLevel=N`
imports anyway — and only if `N` is the level just parsed, so a blind retry cannot
succeed and someone has to have read the number. It exists because there is now a
`DELETE` route but still no sheet editor: a refusal with no way past it would
strand a legitimate homebrew sheet entirely.

**Long prose stays out of the sheet.** Race, background, hit dice and senses are
a few words each and are imported. Features, actions, and proficiencies/languages
are multi-thousand-token blocks of player-editable text, and the `## Current
state` layer they would land in is not wrapped in the untrusted-data markers —
see the residual note below.

**The state layer's budget is now enforced rather than recorded.** Every fixed
layer did `layerTokens.x = Math.min(estimate, budget)` while pushing the
*untruncated* string, so `prompt_total` could be overrun while telemetry reported
compliance. Harmless while sheets were small; a 95-spell character makes it real.
Rendering falls back from a full tier to the core tier — the cut lands on a whole
tier rather than mid-list, and the core tier is byte-for-byte the previous output.

**One new dependency: `unpdf`.** `apps/api` compiles to CommonJS with
`moduleResolution: node10`, which ignores the `exports` map and needs a top-level
`main`/`types`: that rules out `pdfjs-dist` v5 (ESM-only). `pdf-parse` pulls
`@napi-rs/canvas` as a hard dependency, a native build step. `unpdf` has the
top-level fields, inlines its worker, and keeps `@napi-rs/canvas` optional. It is
imported dynamically because its `import` condition is ESM-only and this module is
reachable from Nest's CommonJS build. `multer` was already installed transitively
by `@nestjs/platform-express`, and Nest 12's typings are self-contained, so
neither it nor `@types/multer` was added.

## Plan

1. `packages/contracts/src/sheet.ts` — add `CharacterClass`, `Attack`, `Spell`;
   replace `className`/`level` with `classes[]`; add `attacks[]` and `spells[]`;
   add `characterLevel` and `classLine`; move `level`/`className` into
   `DerivedSheet`. A total-level refinement caps the character, not each class.
2. `apps/api/src/characters/pdf-form.ts` — `readPdfFormFields`, the only file
   that knows about PDFs. Normalises the sheet's inconsistent field-name
   whitespace (`"CLASS  LEVEL"`, `"DEXmod "`, `"Wpn3 AtkBonus  "`).
3. `apps/api/src/characters/wotc-sheet.ts` — the mapping. Pure, so it is tested
   from a JSON fixture with no PDF in the loop.
4. `apps/api/src/characters/characters.controller.ts` — `POST
   /campaigns/:campaignId/characters/import-pdf`, reusing `CharactersService.import`.
5. `apps/web` — `api.ts` stops forcing a JSON content-type on a `FormData` body;
   a file input beside the pregen picker in `Lobby.tsx`; `SheetPanel` renders
   `derived.className`.
6. Fixtures and callers: the six pregens, the DM context's character rendering,
   and four test sheets move to `classes[]`.

**Requirements touched:** FR-401 (derived values recomputed, never stored),
FR-402 (character import), NFR-301 (upload bounds and type checking), NFR-302
(authorization re-checked server-side).

**Known defect, not fixed here.** The same record-but-do-not-truncate bug is in
the `notes` and `action_thread` layers. M8 owns the notes layer; widening this
diff into it would help nobody. Its own follow-up.

**Residual risk, recorded not resolved.** The `## Current state` layer is not
wrapped in the untrusted-data markers, yet it already carried player-authored
strings — inventory item names, up to 120 characters each — and now carries race,
background and senses too. That is a real invariant-7 question, it predates this
change, and answering it means touching the DM contract and every prompt
assertion. Its own issue.

**Not built, named so they are deferrals:** race, background, hit dice, temporary
HP, features and traits, actions, languages and tool proficiencies, personality,
and electrum. Each is reported in `ignored` rather than silently dropped, so the
gap is visible to the player who hits it.
