# Threat model: the config UI (M7.6)

The change puts a credential-entry form and an SSRF-relevant URL field in front
of a human. Nothing new is *possible* — every action here already existed as an
API call — so the question is what the UI makes easy, visible, or misleading.

## The key field

**There is no read path to defend.** The API returns `apiKeyLast4` and never the
key (M7.2/M7.4, asserted in M7.5's suite on every status code). So the page
cannot render a key even if a component tried, and the source scan
(`key-handling.test.ts`) asserts no component tries: no `.apiKey` read anywhere
in `apps/web/src`, `apiKey:` named only on create and replace.

**No reveal affordance, deliberately.** Both key inputs are password fields and
there is no show/hide toggle, because a toggle is the thing screenshots and
screen-shares catch. The scan asserts the absence, so adding one is a failing
test rather than a code-review question.

**Editing cannot blank a key.** The edit form has no key field at all; replacing
is its own form and its own endpoint. The failure mode this prevents is the
common one: a form that submits an empty key field as "set the key to empty",
which would silently break every campaign on that connection.

**The key is typed into a form the browser could remember.** `autoComplete` is
off on both inputs. Beyond that, a credential entered in a browser is in a
browser; the deployment's answer to that is the same as for the sign-in
password, and this change does not make it different.

## The URL field

**The client does not re-implement the SSRF rules.** It sends the URL and shows
whatever the server says (`BASE_URL_REJECTED` plus M7.3's reason). A client-side
copy of the allowlist would drift from the wall that matters and would teach an
admin the wrong rule when it did. The consequence is that the only validation
that exists is the one that is enforced.

**A rejected save keeps what was typed**, which is a usability property with a
security edge: an admin who has to retype a long URL from memory is an admin who
pastes it from somewhere less careful.

## The two audiences

**A host never receives a URL or a key**, and not because this page filters
them: the dropdown is built from `GET /api/providers`, whose `HostConnection`
shape has no field for either. A UI bug cannot leak what the response does not
contain.

**A player can read the campaign's DM settings and cannot write them.** The
read is member-scoped (the table's setup is not a secret from the table); the
write is host-or-admin, enforced by `CampaignMemberGuard` + `CampaignRoles`,
asserted with a 403.

**The Providers button is courtesy, not a control.** It appears when the user is
a platform admin by the same definition the API uses, and hiding it protects
nothing: every route behind it is guarded by `AdminGuard`, re-read from the
database per request. A user who forges the client state gets 403s.

## What the page renders that came from outside

The last-test `detail` (M7.5) is provider-authored text stored in a row. It is
rendered as a text node by React, which escapes it, and it is capped at 500
characters at write time. The campaign names in a delete refusal are
user-authored and render the same way. There is no `dangerouslySetInnerHTML`
anywhere in the app.

## The knobs

Closed vocabularies, validated server-side by the enum, so a host cannot store
arbitrary text in `campaigns.settings` through this route. That matters more
than it looks: those values are destined for the DM's prompt in a later change,
and free text there would be host-authored input arriving where the system
prompt lives (invariant 7). Choosing enums now means that change starts from a
vocabulary rather than from a sanitisation problem — and CL-002 records that the
values are inert until then, so nobody assumes a knob is doing something it is
not.

## Residual, accepted

- No CSRF token. Unchanged from every other mutating call in the app, which
  relies on the session cookie's `SameSite` behaviour; it is not a property this
  change alters, and changing it belongs with the auth work, not here.
- The admin page shows base URLs. Admins set them; the page's audience is
  exactly the audience that already has them.
- No audit of *views*. M7.8 records who changed a connection, not who looked at
  one.
