## Change brief

`readPdf(buffer)` in `apps/api/src/sources/pdf-text.ts` turns campaign-PDF
bytes into `{ totalPages, pages: string[] }` with `pages[i]` = page `i + 1`
(FR-602, partial: text and page references only). A source with no text layer
is refused as `PDF_HAS_NO_TEXT_LAYER` (FR-603 OCR is out, per
docs/campaign-pdf-ingestion.md §2). No table, route or wiring: P4.1.3 is the
only future caller. Design: docs/campaign-pdf-ingestion.md §4.2.

Today nothing in the codebase reads a PDF's text layer; M4.7's
`characters/pdf-form.ts` reads only widget annotations.

## Specification

AC-1  `readPdf` on `fixtures/source-pdfs/two-page-text.pdf` returns
      `totalPages === 2`, `pages.length === totalPages`, and "Klarg the bugbear"
      is in `pages[1]` and not in `pages[0]` (FR-602).
AC-2  `readPdf` on `fixtures/source-pdfs/image-only.pdf` throws a 422 whose body
      is `{ code: 'PDF_HAS_NO_TEXT_LAYER', totalPages: 1, chars: 0 }` with a
      message naming OCR (FR-603 refused loudly).
AC-3  A PDF cut mid-object, a garbage `%PDF-` body, and an empty buffer each
      throw 422 `PDF_UNREADABLE`: never a hang, never empty pages.
AC-4  The caller's buffer is unchanged after `readPdf` (pdf.js detaches what it
      is given; P4.1.1 keeps the original to re-run extraction, FR-611).
AC-5  AC-1 to AC-4 also pass against the compiled
      `apps/api/dist/sources/pdf-text.js` loaded through Node's `require`: the
      CommonJS bundle of unpdf, which vitest does not exercise.
AC-6  build / typecheck / lint / format / test green.

## Decisions

- **D-1: `unpdf` was already a runtime dependency; no dependency is added.**
  M4.7 (#81) added `unpdf@^1.8.1` for the character-sheet import. The epic's
  "one new runtime dependency in total: `unpdf`" was therefore already spent,
  by a different feature. The design doc and the existing code **agree** on
  the library (both use unpdf), so there is no library contradiction; what is
  stale is only the "new dependency" framing in #64/#67 and design §2. This
  change pins it to exactly `1.8.1` (the issue asks for pinned; the lockfile
  already resolved 1.8.1, so nothing resolves differently for #81).
  unpdf 1.8.1: MIT, github.com/unjs/unpdf (npm maintainer johannschopplich),
  published 2026-08-13; seven releases from 1.5.1 (2026-04-13) to 1.8.1.
  `main`/`types` point at `dist/index.cjs`/`index.d.cts`, which is what
  `moduleResolution: node10` needs. No runtime dependencies. `@napi-rs/canvas`
  is an optional peer and is not installed.
- **D-2: error shape aligned with `characters/pdf-form.ts`.** Refusals are
  Nest `UnprocessableEntityException({ code, message, … })`, as the design's
  snippet and the M4.7 reader both do, and a parse failure reuses M4.7's
  `PDF_UNREADABLE` code and message. So the file imports `@nestjs/common` as
  well as unpdf; the issue's "no other imports" is read as "import-light"
  (the CJS/ESM risk is unpdf alone). `unpdf` is imported lazily, as in
  `pdf-form.ts`.
- **D-3: no magic-byte check here.** `looksLikePdf` belongs at the upload
  trust boundary (P4.1.1, design §4.1), where M4.7 also calls it. A non-PDF
  that reaches `readPdf` fails as `PDF_UNREADABLE` anyway (AC-3).
- **D-4: `chars` counts non-whitespace characters**, so a text layer of bare
  line breaks still reads as a scan. Threshold `chars < totalPages * 50`, marked
  `ponytail:`.
- **D-5: the dist smoke check is a vitest suite that `require`s `dist/`.** CI
  builds before it tests, so it always runs there, and it fails rather than
  skips if `dist/` is missing under `CI`. Locally it skips until `pnpm build`
  has run.
- **D-6: fixtures are committed**, hand-built uncompressed PDFs under
  `fixtures/source-pdfs/` (precedent `fixtures/pregens/`), readable with `cat`.
