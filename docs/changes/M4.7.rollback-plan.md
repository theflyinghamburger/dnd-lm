# M4.7 rollback plan

## What can be rolled back cleanly

**The code, without touching the migration.** Reverting to the previous commit
while `characters.level` stays dropped is safe: nothing in either the old or the
new code reads that column. The old code's `sheet->>'level'` expression lives
only in the column definition, not in a query.

This is the ordering that matters, and it is the one a normal `git revert` +
redeploy produces. **Revert code first; leave the migration alone.**

## What cannot

**The stored sheets.** Rolling the code back does not roll back the data. Any
character imported or mutated while M4.7 was live holds `classes[]`, `attacks`
and `spells`, and the previous code casts that straight to its own
`CharacterSheet` and reads `sheet.className` / `sheet.level` — both `undefined`.

The old code has no `parseStoredSheet` and no validation on that path (the cast
this change removed), so the failure is quiet rather than loud: characters render
with `undefined undefined` as their class line and `proficiencyBonus(undefined)`
feeds every derived modifier.

**So a rollback needs the data reversed too**, for rows written under M4.7:

```sql
-- Reverse of the shape change, for single-class characters only.
update characters
set sheet = (sheet - 'classes' - 'attacks' - 'spells' - 'race' - 'background' - 'hitDice' - 'senses')
          || jsonb_build_object(
               'className', sheet->'classes'->0->>'name',
               'level',     (sheet->'classes'->0->>'level')::int)
where sheet ? 'classes'
  and jsonb_array_length(sheet->'classes') = 1;
```

**A multiclass character cannot be reversed** — the old shape has one class and
one level and there is nowhere to put the second. The honest options are to delete
those rows and re-import their sheets, or to collapse them to their largest class
and accept a wrong level. Neither is good, which is the real cost of the rollback
and the reason to prefer fixing forward.

Spells, attacks and the four scalar fields are dropped by that statement. They are
recoverable only by re-importing the source PDF, which the feature never stored.

## Reversing the migration

Only needed if the schema itself must match an older snapshot:

```sql
ALTER TABLE "characters"
  ADD COLUMN "level" integer GENERATED ALWAYS AS (((sheet->>'level')::integer)) STORED;
```

Run it **after** the data statement above, not before: added first, it computes
`NULL` for every not-yet-reversed row and would have to be dropped and re-added.
Drop `apps/api/drizzle/0009_chief_norrin_radd.sql` and its journal entry in the
same commit as the code revert, or `pnpm db:check` will report drift.

## Partial rollback of individual pieces

Each fix in this change is independently revertible, and none of them requires
the others:

| Piece | Reverting it |
|---|---|
| `DELETE /characters/:id` | Remove the route. No data implication — deletions already taken stay taken, and `rolls.character_id` is `ON DELETE SET NULL`, so roll history is intact either way. |
| `confirmLevel` override | Remove the query parameter. Characters imported through it keep the level they were confirmed at; nothing re-checks on read. |
| `parseStoredSheet` | Do **not** revert this alone. It is what lets old rows be read; without it they throw. |
| The state-layer budget | Revert to `render('full')` with no fallback and the prompt can overrun `prompt_total` again (FR-701). Prompt size only, no data. |

## Blast radius

No user data is destroyed by the forward migration. The only irreversible loss
sits on the *rollback* path — multiclass characters, spells and attacks, as
above. There is no production deployment, so today the realistic recovery for any
of this is to truncate `characters` and re-import.
