# Threat model: audit and attribution (M7.8)

The change adds a table that records what admins do and two fields that record
what the DM ran on. Both are new places for information to end up, so the
question is what could end up there that should not.

## The audit table

**It records names, never values.** `changed_fields` is a diff of the admin DTO
against the stored row, expressed as column names (`base_url`, `api_key`,
`enabled`). There is no column that could hold a key, a ciphertext, or a URL,
and the e2e suite asserts it by scanning whole rows for every value that passed
through the API — the key, the rotated key, both URLs, the labels, the model id.
A value in this table would be a second copy of a secret with none of the first
one's protections (it is not encrypted, and unlike `provider_connections` it is
never meant to be deleted).

**`replaced_key` is the sharpest case.** It names the field and nothing else:
not a fragment, not a last4, not a length. The suite asserts the exact array.

**Write path is the mutation's own transaction.** A change without its audit
row, or an audit row without its change, would both be worse than neither: the
first hides an action, the second invents one. A failed mutation — an M7.3 URL
rejection, a 404, an in-use delete — writes nothing, which the suite asserts by
counting rows after each failure.

**Durability over referential integrity, on purpose.** No foreign key to
`provider_connections`: a cascade would erase the `deleted` row, which is the
single most interesting record in the table. `actor_user_id` keeps its key with
`ON DELETE SET NULL`, so removing a user redacts the actor and preserves the
action. Both are stated in the schema comment so a later reader does not "fix"
them.

**Who can read it.** Nothing exposes the table over HTTP in this change. It is
operator-facing, reachable through the database. Adding a UI for it later means
deciding who may read an actor's history — a question this change deliberately
does not answer.

## The attribution fields

**They carry an id and a model name, both already visible to admins.**
`provider_connection_id` and `model_id` go onto `DM_NARRATION` and
`DM_RESOLUTION_FAILED` payloads, which reach the table's clients. Neither is a
secret: the host-facing connection list (M7.4) already returns id and model by
design, precisely so a host can choose one. The base URL and the key are on
neither event, and the `HostConnection` shape they would have to come from does
not contain them.

**A player learns which model answered.** That is the intent — "which model
answered" is a question the client may want to render — and it is worth stating
plainly rather than discovering later. It reveals the deployment's model
choice, not its endpoint or its credentials.

**A failure carries null rather than a guess.** `NO_PROVIDER` means no
connection was resolved; the event says so with nulls instead of reporting the
campaign's *selected* connection, which may be exactly the row that was disabled
or deleted. A guessed attribution in a forensic field is worse than an absent
one.

## The rollup query

The per-connection failure-rate and cost query reads `session_events` only. It
groups on a payload field, so a resolution written before this change groups
under `NULL` — visible as "unattributed", never silently merged into a
connection's numbers.

## Residual, accepted

- The audit table grows without bound. Provider mutations are rare (one row per
  admin action on a handful of connections); a retention policy is not worth
  writing before there is a volume problem.
- An admin with database access can edit or delete audit rows. The table is an
  audit trail for humans reviewing what happened, not tamper-proof storage; the
  application never updates or deletes a row it wrote.
- `changed_fields` records that a field moved, not what it moved from or to. A
  reconstruction of past configuration is not possible from this table, and is
  not meant to be — the value history is where the secrets would live.
