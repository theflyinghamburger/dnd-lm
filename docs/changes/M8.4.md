## Change brief

`@npc Klarg` has answered "unknown NPC" since M3 because
`SessionContextService.forCampaign` builds the roster with a hard-coded empty
NPC list. This subtask (#51, M8 #9) fills that list from `type = 'npc'`
`campaign_notes` under the same hard filters as M8.2 retrieval, so an NPC the
party has not met reads exactly like an unknown one (MVP.md §4.3 rules 2 and 4).
Resolution logic (`resolveNpc`, `buildRoster`, the rejection path in
`packages/contracts`) is unchanged. No note write path (M8.5), no DM context
change (M8.3).

## Specification

AC-1  `@npc klarg …` on a campaign with a published, player-level NPC note
      titled `Klarg` (slug `location.klarg`) emits `DM_TRIGGERED` with
      `definition_id` `npc_mention`, `entry_profile` `npc_dialogue`,
      `args.entityId` `location.klarg` (FR-206, rule 4).
AC-2  The same resolves by a unique `frontmatter.aliases` entry; non-string
      entries and a non-array `aliases` are dropped, never thrown on.
AC-3  Two NPC notes with the same title: `AMBIGUOUS_NPC`, no message stored,
      no `DM_TRIGGERED`.
AC-4  An NPC note with `chapter` above `settings.progression.chapter`, a
      `dm`-level NPC, a `draft` NPC, another campaign's NPC, and a non-`npc`
      note are all rejected with `UNKNOWN_NPC` and the exact message a
      nonexistent name gets, even when the name matches exactly; none appears
      in `GET /campaigns/:id/roster`.
AC-5  An NPC note named like a reserved handle (`DM`) is addressable via
      `@npc DM`, and `@dm` still parses to `dm_mention` against the served
      roster (rule 3).
AC-6  After a note is written and `SessionContextService.invalidate` is called,
      the next message routes against the new roster with no restart.
AC-7  The existing unknown-NPC and disabled-trigger routing cases stay green;
      build/typecheck/lint/format/test green against live Postgres.

## Decisions

- **The roster is `player`-level for every sender.** It is served verbatim to
  every member by `GET /campaigns/:id/roster` (the composer's FR-209 preview),
  so a `dm` NPC in it would leak its name to players. One per-campaign cache
  stays one cache (NFR-101). Consequence: the host cannot `@npc` a `dm`-level
  NPC either; publishing it at `player` level is how it becomes addressable.
- **`NotesService.npcs(campaignId, chapter)`, a new method**; `retrieve` is not
  touched (M8.3, PR #98, changes its query). The four predicates are repeated,
  not shared, to keep the merge with #98 trivial.
- **`spoiler_level = 'player'` as `eq`, not `lte`** — with two levels it is the
  same, and a future third level fails toward hidden.
- **Chapter: `settings.progression.chapter`, junk or absent reads 0**, matching
  #98's `DmContextReader` rule.
- **No contracts change** — server-side only, so the profile stays `standard`
  (raised from the path floor `fast`: it is a spoiler boundary, as M8.2).
- **Invalidation**: there is no note write path yet (M8.5). The test calls the
  existing `invalidate` seam directly after a DB write, which is the call M8.5
  will make.
- **Mutation-checked**: deleting each of the campaign, status, spoiler and
  chapter predicates fails the AC-4 test.
