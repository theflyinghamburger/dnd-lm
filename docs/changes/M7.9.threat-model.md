# Threat model: provider failure behaviour (M7.9)

A failure path is where information leaks, because it is where systems say more
than they meant to. This change makes one audience's channel richer, so the
question is whether any of it reaches the other.

## The player channel

**The event's `message` is a lookup, not a formatted string.** It comes from a
`Record<DmFailureReason, string>` of six constants. There is no interpolation
anywhere on that path, so no provider text, URL, model id, key fragment or
status code can reach it by accident — a leak would require someone editing the
constants. The suite asserts the sentence for each failure class and asserts the
absence of the base URL, the port, the key, the model id, and the SDK's own
words.

**The failure *reason* is deliberately coarse.** Unreachable, unauthenticated
and model-not-found all arrive as `PROVIDER_ERROR`. A player watching the
closed enum cannot distinguish "the DM's endpoint is down" from "the key is
wrong", which is the intent: the fine class exists only in the operator line.
`DmFailureReason` does not grow, so a future class cannot leak by being added
to the client-facing set.

**The attribution fields stay, and that is a considered exception.**
`provider_connection_id` and `model_id` are separate payload keys (M7.8), not
part of the message, and the tests assert both halves so that collapsing them
fails loudly (CL-001). A player learns which model answered — an identity the
host-facing list already publishes — never the endpoint or the credential.

## The operator channel

**Everything on the line passes redaction first.** The graph redacts the
provider's text with the connection's own key at the point of classification;
the orchestrator redacts stacks and commit errors the same way. The suite runs
a mock endpoint that echoes the key back in a 401 body — the phrasing real
providers use — and asserts the line contains `[REDACTED]` and not the key.

**The line still contains the provider's own words.** That is the point of it,
and it means a hostile endpoint can write chosen text into the operator's logs.
Two bounds: it is one line per failed resolution with whitespace collapsed, so
it cannot forge extra log lines with embedded newlines, and the detail is JSON
quoted, so quotes and control characters cannot break the field format. What it
cannot be bounded against is volume — see residual.

**Log destination is unchanged.** This is Nest's logger, wherever the
deployment already sends it. The change adds no new sink, no file, no HTTP
surface. Who can read the logs is the deployment's question, and it was already
being asked of the stacks these lines replace.

## Failing over, and why it does not

`NO_PROVIDER` and `PROVIDER_ERROR` end the turn. There is no second connection
tried, in this turn or a later one, and the campaign's selection is never
rewritten by a failure — the test asserts both the zero call count on the spare
connection and the untouched selection. The value here is not
confidentiality, it is continuity: a silent switch to another model mid-session
changes the DM's voice and its context handling in a way nobody consented to,
and it would do so precisely when the operator is least likely to be watching.

## Residual, accepted

- **A misconfigured connection is a log amplifier.** Every triggered turn
  writes one line, and a table that keeps poking `@dm` at a broken provider
  writes one per poke. Bounded by the existing per-session rate limiting on
  messages and by there being one line, not a stack, per failure. A summarising
  or sampling layer is a monitoring decision, not an MVP one.
- **A rejected credential is retried once** before the failure is reported
  (M6.7's bounded retry, unchanged). That is one extra call to an endpoint that
  has already refused the key.
- **The class vocabulary is a string, not an enum, on the log line.** It is
  operator-facing text with no client contract; typing it would buy nothing and
  would tempt someone to expose it.
