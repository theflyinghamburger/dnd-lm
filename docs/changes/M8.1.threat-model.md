# Threat model: notes storage (M8.1)

This change adds a table and no code path that reads or writes it. The threats
are therefore about the shape — what the later milestones will be able to get
wrong because of a choice made here.

## Spoiler leakage (FR-608)

The spoiler guarantee M8.2 promises is a SQL predicate,
`spoiler_level <= $scope`, and it is only correct because Postgres compares
enum values by declaration order and `note_spoiler_level` declares
`('player', 'dm')`. A later edit that reorders the list, or inserts a new
level in the wrong place, silently inverts the filter — players would receive
DM-only notes and nothing would error. Controls: the schema comment says so in
capitals; the e2e suite asserts `<= 'player'` excludes `dm` notes, so a
reordering fails a test rather than a playtest.

**Fail-closed default.** `spoiler_level` defaults to `dm`. A note written
without a level — a hand insert, a fumbled ingestion record — is hidden from
players rather than exposed. Asserted.

**Drafts.** `status` defaults to `published` for hand-authored notes; Phase 4
writes `draft`. The `status = 'published'` predicate is M8.2's to add. Until
then no read path exists, so there is nothing to leak through.

## Cross-campaign leakage

`campaign_id` is `NOT NULL` with a foreign key; slugs are unique per campaign
only, so two campaigns can hold the same slug. That makes `slug` alone an
unsafe lookup key — every future read must also filter on `campaign_id`. The
unique index leads with `campaign_id`, so the correct query is also the
indexed one. M8.2's acceptance test ("a note from campaign A never appears in
B's retrieval") is the enforcement.

## Untrusted content (invariant 7)

`title`, `body_md` and `frontmatter` will hold host-written and, later,
book-extracted text. Storing it is not a risk; *interpolating* it into a
prompt outside the untrusted-data markers would be. This change adds no reader.
`to_tsvector` treats the text as data; it has no injection surface.

## Deletion (FR-611)

Notes cascade from their campaign — a note has no life of its own and must not
outlive a deleted campaign. Asserted. `source_id` will be `ON DELETE SET NULL`
once P4.1.1 adds the constraint, so deleting an upload keeps the notes a host
may have edited.

## Denial of service

`tsv` is computed on every insert/update of `title`/`body_md`. Cost is linear
in text length; there is no write path yet, and M8.5 / P4.1 own the size caps
on what they accept.

## Residual, accepted

- `source_id` carries no foreign key until P4.1.1; until then nothing writes
  it, so a dangling value cannot arise in practice.
- `frontmatter` is unvalidated JSONB at the database layer. Its shape is
  enforced where it is written (M8.5 API, P4.1.3 Zod parse), consistent with
  `campaigns.settings`.
