# Rollback plan — M7.8

**Code alone (no schema change).** Revert the PR. The table stops being written
and nothing reads it; the two event payload fields stop being emitted, and
events already carrying them stay valid because `EventEnvelope.payload` is an
open record. Clients that learned to render "which model answered" fall back to
not showing it. This is the expected rollback and needs no database work.

**Schema too, if the table must go:**

```sql
DROP TABLE "provider_connection_audit";
DROP TYPE  "public"."provider_connection_audit_action";
```

Then delete `apps/api/drizzle/0008_clever_purifiers.sql`, its snapshot, and the
`__drizzle_migrations` row, so `pnpm db:check` agrees with the committed
migrations again. Revert the code first: a build that still writes audit rows
fails **every provider mutation** once the table is gone, because the write is
inside the mutation's transaction. That is the intended coupling — an
unaudited mutation should not succeed — and it makes the order non-optional.

**Data lost.** The whole audit history. It is not reconstructible from anything
else: `provider_connections.updated_at` records only the latest write, and the
event log knows nothing about configuration changes. If the table is being
dropped for a reason other than "this feature was a mistake", dump it first:

```sql
\copy provider_connection_audit TO 'provider_connection_audit.csv' CSV HEADER
```

**Partial rollback that is usually the right one.** If the problem is the
coupling rather than the record, revert only step 3 of the plan (the service
transactions) and keep the table: mutations stop being blocked by an audit
failure, and the history stays readable. Nothing else in the change depends on
the audit write.

**The attribution half rolls back independently.** Reverting the payload fields
and the span attribute touches no schema at all; the rollup query then reports
`NULL` for turns taken after the revert, which reads correctly as
"unattributed" rather than as a wrong connection.
