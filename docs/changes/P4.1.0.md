## Change brief

`DmRequest.maxTokens` (`apps/api/src/dm/provider.ts`) is dead: both adapters
send `max_tokens: this.config.maxTokens`, the connection row's value, whatever
the caller asked for. P4.1.3's extraction call needs a ceiling above the row's
1024 default, so the request field has to reach the wire.

Callers today (verified): the graph's `callDm` node passes
`sourced.config.maxTokens` — the same row value the adapter was built with — and
`ConnectionTestService.run` (the M7.5 test action; the issue's "third caller" is
the same code path) passes `TEST_MAX_TOKENS = 256`. No caller passes 0 or omits
the field; the type makes it required.

## Specification

AC-1  Each adapter, given `generate({ …, maxTokens: 4000 })`, sends
      `max_tokens: 4000` to its SDK.
AC-2  Each adapter, given `maxTokens: 0` or no `maxTokens`, sends the
      connection's `max_tokens`.
AC-3  A DM turn on a connection with `max_tokens: 777` sends `max_tokens: 777`
      end to end (row -> graph -> adapter -> HTTP), and a turn on a default row
      sends 1024 — the turn's ceiling is unchanged by the fix.
AC-4  The existing M7.5 connection-test suite and DM e2e suites stay green.
AC-5  build / typecheck / lint / format / test green against live Postgres.

## Decisions

- **D-1 — `||`, not `??`**, as the issue specifies: 0 is not a meaningful
  ceiling, so it falls back to the row along with `undefined`.
- **D-2 — Known behaviour change, not fixed here:** the M7.5 connection test now
  really sends 256 instead of the row's value. That is what its caller always
  intended (`TEST_MAX_TOKENS`'s comment), but on the Anthropic adapter, which
  sends `thinking: { type: 'adaptive' }`, a 256-token ceiling shared with
  thinking could truncate the dm-json block and report `structuredOutput:
  false` against a real endpoint. Out of scope per the issue ("Nothing else");
  tracked as #87.
