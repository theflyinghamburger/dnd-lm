# Threat model: Test connection (M7.5)

The action makes the server issue an outbound request to a URL a human typed
into a form, using a credential the server holds, and stores what comes back.
Each of those three is a boundary.

## The outbound request

**A test does not open a hole the DM turn did not already have.** It builds its
provider through `ProviderConnectionsService.sourceFromRow`, the same path M7.7
resolves a turn with, so the M7.3 wall applies unchanged: `validate` at build
time, and `resolvedIpFetch` pinning the connect to the address that check
approved. A URL the policy stopped allowing fails the test with `reachable:
false` and a reason, which is the correct answer and not a bypass.

**It is an internal-network oracle only where the DM already is one.** An admin
can learn "something answered / refused" for any URL the SSRF wall permits.
That capability is not introduced here — an admin who can save a connection can
select it and take a turn — and it is bounded by the same allowlist, private
range and link-local refusals (`169.254.169.254` most of all).

**The rate limit is a cost ceiling, not a security control.** Five presses per
minute per connection, in process. It stops a fat finger and a bored admin, not
a determined one, and a multi-process deployment multiplies it by the process
count. It is stated that way in the code comment so nobody later mistakes it for
a defence.

## The credential

The key is decrypted in memory to build the adapter and never leaves it: the
response DTO is `ConnectionTestResult`, which has no key field, and the row
write touches only `last_test_result`. The one channel that could carry key
material is `detail`, because providers quote the credential they rejected —
`Incorrect API key provided: sk-...` is the literal OpenAI phrasing. Every
`detail` therefore passes through `ProviderSecrets.redact` with the connection's
own key, and the e2e suite asserts the redaction on a mock endpoint that echoes
the key back in a 401 body.

## What comes back

**The provider's error text is attacker-influenced data on its way into our
database.** A hostile or broken endpoint answers whatever it likes, and the
result lands in a row an admin page (M7.6) will render. Two mitigations:
`detail` is capped at 500 characters after redaction, so an endpoint cannot use
a test press as an unbounded write; and it is stored as data in a `jsonb`
column, rendered by React as text, never as markup or HTML.

**A stored result is a claim about a past moment, not a live status.** The
timestamp travels inside the object for exactly this reason. A connection that
passed an hour ago can be failing now; nothing in M7.5 or M7.6 should be read as
monitoring, and the UI shows when the result was taken.

## Authorization

The route sits behind the existing `AdminGuard` — an `admin` membership in some
campaign (M7.4, option (a)) — re-read from the database on every request. A
non-admin gets 403 before any provider call is made, and the suite asserts the
call count is zero on that path, not merely the status code.

## Residual, accepted

- `modelExists` means "the endpoint accepted this model id". An endpoint that
  accepts the id and serves a different model passes the test. Detecting that
  needs a second round trip no provider guarantees; the field's meaning is
  documented rather than overstated.
- The in-process rate limit resets when the API restarts.
- A test spends provider tokens. That is the point of the action, and why it
  fires only on an explicit press — never on page load, save, or list, which the
  suite asserts by call count.
