# Migration plan — P4.1.1

`apps/api/drizzle/0011_lean_mockingbird.sql` (generated by
`pnpm db:generate`, not hand-edited):

- `CREATE TYPE source_status AS ENUM ('pending','extracting','review','failed')`.
- `CREATE TABLE campaign_sources (…)` with FKs
  `campaign_id → campaigns ON DELETE CASCADE` and
  `uploaded_by → users ON DELETE SET NULL`.
- `campaign_sources_one_in_flight_key` — unique btree `(campaign_id)` `WHERE
  status IN ('pending','extracting')`; `campaign_sources_campaign_idx` btree
  `(campaign_id, created_at)`.
- `ALTER TABLE campaign_notes ADD CONSTRAINT
  campaign_notes_source_id_campaign_sources_id_fk FOREIGN KEY (source_id)
  REFERENCES campaign_sources(id) ON DELETE SET NULL` — the constraint M8.1
  deferred. Constraint only: no column, no rewrite.
- `CREATE INDEX campaign_notes_source_id_idx ON campaign_notes (source_id)` —
  Postgres does not index the referencing side of an FK, so without it every
  source delete scans `campaign_notes` to null its notes. Built while the
  column is all-NULL, so it is tiny; a plain (locking) `CREATE INDEX` is fine
  at this size.

**Shape.** A new enum and empty table, plus one constraint on
`campaign_notes`. `ADD CONSTRAINT … FOREIGN KEY` takes a `SHARE ROW
EXCLUSIVE` lock on `campaign_notes` and scans it to validate. Nothing writes
`source_id` yet (M8.1 has no writer; P4.1.3 is the first), so every existing
row is `NULL` and validation passes trivially; the table is small or empty.
If a hand insert ever set a non-null `source_id`, the migration fails loudly
rather than corrupting anything — find them with
`SELECT id FROM campaign_notes WHERE source_id IS NOT NULL` and null them.

**Deploy order.** The previous build never touches `campaign_sources`, and
the FK only constrains a column the previous build does not write. Migrate
before or after deploy; either works.

## Parallel-branch collision

M8.2 (`m8.2-retrieval`) is stacked on the same base (#90). If it also
generates a migration, both are `0011`. Whichever merges second deletes its
generated SQL + snapshot + journal entry, rebases, and reruns
`pnpm db:generate` so the snapshot chain stays linear; CI's drift check fails
otherwise.

## Verification

`pnpm db:migrate` on live Postgres, `pnpm db:check`, CI's
regenerate-and-diff drift job, and `apps/api/test/campaign-sources.e2e.test.ts`
(SET NULL on source delete, CASCADE on campaign delete, the partial index
refusing a second and a concurrent in-flight upload).
