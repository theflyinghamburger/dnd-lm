# M4.7 migration plan

Two shape changes ship together: one to the database, one to the JSONB the
database stores.

## 1. Schema — `0009_chief_norrin_radd.sql`

```sql
ALTER TABLE "characters" DROP COLUMN "level";
```

**What it was.** A generated column, `GENERATED ALWAYS AS ((sheet->>'level')::integer) STORED`,
added in `0003_burly_orphan.sql`.

**Why it goes.** M4.7 replaced `sheet.level` with `sheet.classes[]`, so the
expression reads a key that no longer exists. Verified against Postgres:

| sheet | `(sheet->>'level')::integer` |
|---|---|
| `{"classes":[{"name":"Artificer","level":5},…]}` | `NULL` |
| `{"className":"Fighter","level":3}` | `3` |

It cannot be repaired in place. Summing `classes[]` needs
`jsonb_array_elements`, a set-returning function, and a generated column may not
contain one — nor a subquery.

**Why dropping is safe.** Nothing reads it. The only other `characters.level`
occurrence in the tree is unrelated prose in `dm/context.ts`. The character's
level is `characterLevel(sheet.classes)`, computed on read like every other
derived value (FR-401, D-3) — which is what the column should never have been.

**Data loss.** For rows written since the shape change, none: the column was
already `NULL`. For older rows the stored integer is discarded, and it is exactly
reproducible from `sheet` at any time — which is what made it a generated column
in the first place.

**Order.** Column-only, no data movement, no lock beyond a brief `ACCESS
EXCLUSIVE` on `characters` for the catalogue update. Instant at any table size
this project will see. Apply with `pnpm db:migrate`; `pnpm db:check` must come
back clean afterwards, and CI's drift job fails if the snapshot and schema
disagree.

## 2. Stored sheets — no migration, by design

Rows written before M4.7 hold `{className, level, …}`. There is **no data
migration and no one-shot script**; `parseStoredSheet` in
`packages/contracts/src/sheet.ts` reshapes them on read, and it is the single
function every read path now goes through in place of the unchecked
`row.sheet as CharacterSheet` cast it replaces.

Two consequences worth stating plainly:

- **Old rows keep working immediately**, with no operator step and nothing to
  forget. That matters more than tidiness here: a migration that must be run is
  a migration someone can skip, and skipping it would break every character read.
- **Rows heal as they are touched.** The orchestrator's HP and inventory writes
  round-trip the parsed sheet (`dm/orchestrator.ts`), so a row is rewritten in the
  new shape the first time the DM changes it. `updateHp` uses `jsonb_set` on a
  single key and does not reshape — harmless, just not healing.

The legacy branch is marked `ponytail:` with the query that says when it can go:

```sql
select count(*) from characters where sheet ? 'className';
```

Delete the branch when that is `0` and stays `0`.

**A corrupt row now fails loudly.** Parsing rather than casting means a
structurally broken sheet raises at the read boundary naming the offending field,
instead of throwing from inside `deriveSheet` with no indication of which row. The
HTTP response stays a bare 500 — a bad stored row is an internal fault and its
shape is not the caller's business.

## Verification after applying

```sh
pnpm db:migrate && pnpm db:check          # clean
set -a; source .env; set +a; pnpm exec vitest run
```

`apps/api/test/character-lifecycle.e2e.test.ts` inserts a legacy-shaped row
directly — no route can produce one any more — and asserts it lists, derives, and
is not silently rewritten on read.
